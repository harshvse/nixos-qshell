# Wallpaper-driven theming system

Source: `home/programs/wallust.nix` (the engine), plus the theming-relevant
parts of every other `home/programs/*.nix` file. This is the subsystem that
ties the rest of the docs together — read this one first if you're trying
to understand why `kitty.nix`, `waybar.nix`, etc. look the way they do.

## The problem this solves

Changing the wallpaper should re-theme the terminal, status bar, launcher,
notifications, editor, and GTK/Qt apps together, instantly, without a
`nixos-rebuild`. A prior iteration of this repo (`home/theme.nix`, now
deleted) hardcoded one static palette at Nix build time; this replaced it.

## Core architecture

**Palette engine: [wallust](https://codeberg.org/explosion-mental/wallust)**
(a Rust rewrite of pywal). `wallust run <image>` extracts a 16-color palette
from an image and renders it into template files.

**The split, applied consistently per app:**
- *Structural* config (layout, keybinds, fonts, module lists) is
  Nix-managed as normal.
- *Color* values live in a file **outside the Nix store**, generated by
  `wallust run`. Nix-managed config `include`s/`@import`s that file at its
  *runtime* path (or, for apps with no include mechanism, wallust owns that
  app's whole config file directly).

This means Nix never bakes a color value into a build — `wallust run`
regenerates the target file, and each app reloads without a rebuild.

**Critical rule**: none of the wallust-generated target paths are
home-manager-managed (no `xdg.configFile` pointing at them). A
home-manager-managed file is a read-only symlink into the Nix store;
wallust needs to overwrite these as plain mutable files on every run. Only
their *parent directories* are ensured to exist (via `wallust.nix`'s
activation script). This is why `mako.nix` and `btop.nix` look almost empty
— see below.

## `wallust.toml` — the template registry

Managed at `~/.config/wallust/wallust.toml` (this file itself is fine to be
Nix/store-managed — wallust only reads it). Each `[templates.<name>]` entry
maps a template file (under `~/.config/wallust/templates/`, also
Nix-managed since they're read-only source material) to a runtime `target`:

| Template | Target | Consumed by |
|---|---|---|
| `kitty.conf` | `~/.cache/wallust/kitty-colors.conf` | kitty, via `include` |
| `waybar.css` | `~/.cache/wallust/waybar-colors.css` | waybar, via `@import` |
| `wofi.css` | `~/.cache/wallust/wofi-colors.css` | wofi, via `@import` |
| `hyprland-colors.lua` | `~/.cache/wallust/hyprland-colors.lua` | Hyprland, via `dofile()` |
| `nvim-colors.lua` | `~/.cache/wallust/nvim-colors.lua` | Neovim, via `dofile()` |
| `gtk-accent.css` | `~/.cache/wallust/gtk-accent.css` | GTK3/4, via `@import` |
| `mako-config` | `~/.config/mako/config` | mako — wallust owns this file outright |
| `btop.theme` | `~/.config/btop/themes/wallust.theme` | btop — wallust owns this file outright |
| `fastfetch.jsonc` | `~/.config/fastfetch/config.jsonc` | fastfetch — wallust owns this file outright |

Template syntax is Tera/Jinja2-like: `{{background}}`, `{{foreground}}`,
`{{cursor}}`, `{{color0}}`–`{{color15}}`.

## `[hooks]` — reload orchestration

Also in `wallust.toml`, run after templates render:

```toml
[hooks]
kitty    = "kitty @ --to unix:/tmp/kitty-wallust-socket load-config >/dev/null 2>&1 || true"
waybar   = "pkill -SIGUSR2 waybar >/dev/null 2>&1 || true"
mako     = "makoctl reload >/dev/null 2>&1 || true"
hyprland = "hyprctl reload >/dev/null 2>&1 || true"
```

- **kitty**: needs a *fixed* control socket path (`listen_on =
  "unix:/tmp/kitty-wallust-socket"` in `kitty.nix`) because these hooks run
  outside any kitty session, so `$KITTY_LISTEN_ON` isn't set — the hook
  can't rely on kitty's usual per-instance auto socket.
- **waybar**: no live CSS reload API; `SIGUSR2` is the documented way to get
  it to reload.
- **mako**/**hyprland**: `makoctl reload` / `hyprctl reload` are the normal
  CLI reload commands, unrelated to wallust specifically.
- **Neovim and GTK/Qt apps are deliberately not in this hook list** —
  Neovim re-reads its palette only at startup (see [neovim.md](neovim.md)),
  and already-running GTK/Qt apps don't hot-reload CSS/theme changes; only
  new instances pick up a change. This is a known, accepted limitation, not
  an oversight.

## First-boot seeding

`home.activation.wallustSeed` (in `wallust.nix`) runs on every
`nixos-rebuild switch`, but only *acts* when `~/.cache/wallust/` is empty:

1. Ensures `~/Pictures/wallpapers/`, `~/.cache/wallust/`, and the
   mako/btop/fastfetch config dirs exist.
2. If no wallpaper exists yet, generates one with ImageMagick:
   `convert -size 1920x1080 plasma:fractal <path>`.
3. Runs `wallust run` against it once.

**Gotcha discovered the hard way**: the first version of this used
`gradient:'#1e1e2e-#313244'` (a plain 2-color linear gradient) as the
placeholder. wallust's palette extraction failed on it with `Error: Not
enough colors!` — a 2-stop gradient doesn't have enough distinct pixel
colors to build a 16-color palette from. The `|| true` on the wallust
invocation swallowed the failure silently, leaving the cache empty and
every wallust-owned config file (mako, btop, fastfetch) never created.
Switched to ImageMagick's `plasma:fractal` pseudo-image (a colorful fractal
noise pattern) instead — verified working by running `wallust run` against
it directly. If you ever change the seed image generator, sanity-check it
the same way before trusting the activation script.

## The wallpaper picker

`home/programs/wofi.nix` builds a `wallpaper-select` script
(`pkgs.writeShellApplication`) bound to `SUPER+W` in `hyprland.nix`:

```bash
selected=$(find "$HOME/Pictures/wallpapers" -maxdepth 1 -type f | sort | wofi --dmenu -p "Wallpaper")
[ -z "$selected" ] && exit 0
awww img "$selected" --transition-type wipe --transition-fps 60
wallust run "$selected"
```

wofi has no image-preview mode (unlike rofi) — this is a plain filename
list, not thumbnails. Known limitation, not a bug.

## The `swww` → `awww` rename

nixpkgs renamed the `swww` wallpaper daemon package to `awww` upstream —
`pkgs.swww` still resolves (with a deprecation warning) but the package's
binaries are actually named `awww` and `awww-daemon`, not `swww`/
`swww-daemon`. This was caught by literally building the config and
inspecting the resulting store path's `bin/` contents — every script and
the Hyprland autostart block in this repo uses the new `awww`/`awww-daemon`
names directly. If you see `pkgs.swww` referenced anywhere with the old
binary names, that's a bug.

## Hyprland autostart integration

`hyprland.nix`'s `hl.on("hyprland.start", function() ... end)` block
launches, once per compositor start (not on every config reload):

```lua
hl.exec_cmd("awww-daemon")
hl.exec_cmd("sleep 0.5 && awww restore")
hl.exec_cmd("waybar")
hl.exec_cmd("mako")
```

`awww restore` reapplies whatever wallpaper was last set, so a logout or
config reload doesn't reset the desktop to a blank background.

**Important operational note**: because this only fires on a *fresh*
Hyprland start, a live session that predates this config change won't have
these daemons running until you log out/in (or reboot) — `hyprctl reload`
alone does not re-trigger `hyprland.start`. If wallpaper switching seems
"not working," check first whether `awww-daemon`/`waybar`/`mako` are
actually running (`pgrep -a -f 'awww|waybar|mako'`) before assuming the
config itself is broken.

## GTK/Qt: an honest scope boundary

Fully recoloring arbitrary GTK/Qt chrome to match a wallpaper's exact
palette isn't realistic without a much heavier tool (e.g. Gradience). What's
actually delivered — see [gtk-qt.md](gtk-qt.md) for the full breakdown:
- GTK3/4 gets a fixed dark base theme *plus* a genuinely wallpaper-reactive
  accent color (selections, scrollbars, focus rings) via `extraCss`.
- Qt (qt5ct/qt6ct + Kvantum) is paired to the same dark base but is
  **static**, not wallpaper-reactive — Kvantum's color-override format
  wasn't verified enough to template safely.

## Verifying the whole loop

1. `SUPER+W` → pick a wallpaper.
2. Within ~1s: kitty's `include`d colors change (reload via kitty's
   remote-control hook, or open a new window), waybar restarts styled,
   `notify-send test` shows themed colors, `hyprctl reload` picks up new
   border colors, and a freshly launched `btop` shows the new theme.
3. A **freshly opened** Neovim instance picks up the new palette (existing
   buffers don't, by design — see [neovim.md](neovim.md)).
4. A **freshly launched** GTK/Qt app reflects the new accent color; already
   running ones don't (also by design).
